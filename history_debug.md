# WatchDrip2 background widget debug history

Короткая история проверок по проблеме: виджет/карточка WatchDrip2 на Zepp OS 3+ не обновляет сахар в фоне. Если открыть основное приложение на часах, данные обновляются; если оставаться на циферблате/виджете, возраст данных продолжает расти.

## Что уже подтверждено

- Телефонный side-service отвечает: при открытом приложении видны `WATCH_REQ`, `FETCH_REQ`, `FETCH_RES Success`.
- Основное приложение на часах умеет получать свежий `info.json` и обновлять UI.
- Виджет читает локальный `info.json` и корректно отображает уже сохраненные данные.
- На часах разрешена фоновая активность для WatchDrip2; в настройках часов WatchDrip2 включен как фоновое приложение.
- Публичной полезной информации по точной проблеме Zepp OS 3+ widget background fetch почти нет; локальная спецификация полезнее.

## Что уже пробовали

- Исправили `@zos/app-service.start()` на `file: 'app-service/index'`, потому что для start/stop нужен `file`, не `url`.
- Добавили permission `device:os.bg_service` в `app.json`.
- Добавили `queryPermission/requestPermission` для `device:os.bg_service` из app/page/widget.
- Пробовали запускать App Service из `app.js`, `page/index.js` и `data-widget/index.js`.
- На скриншоте диагностическая строка показывала `page_service_start_cb r=false`: continuous App Service отклоняется системой.
- Прямой BLE/MessageBuilder-fetch из widget ранее ломал установку/пакет, поэтому от него отказались.
- Добавили `@zos/alarm` для фонового запуска `app-service/index.js`.
- Пробовали repeat alarm через `REPEAT_MINUTE`; надежного обновления виджета не получили.
- Переключили alarm на одноразовый самоперепланируемый запуск service.
- Из App Service убрали обычные JS timers/polyfill и сделали short-run: fetch по alarm, затем `exit()`.
- Добавили persistent debug stage в config и временную debug-строку на app/widget.
- Увеличили толщину полосы виджета до `px(16)` и выровняли UI по карточке.
- Устанавливали сборки на реальные часы через `zeus bridge`; последняя попытка также не решила проблему по отчету пользователя.

## Наблюдения

- Пока приложение открыто, fetch идет примерно раз в минуту, но это не доказывает фон.
- `processInfo list` показывает только наличие процесса, не факт успешного обновления данных.
- Если bridge показывает успешный fetch, а виджет все равно стареет, возможна отдельная проблема repaint/cache виджета.
- Если bridge не показывает fetch после закрытия приложения, проблема в wake/start background path.
- Текущая рабочая гипотеза: Zepp OS 3+ на этих часах не дает автоматически стартовать continuous App Service из widget/page, и может требовать явный пользовательский запуск/разрешение внутри приложения либо другой wake-механизм.

## Что еще не доказано

- Срабатывает ли `@zos/alarm` именно когда основное приложение закрыто и открыт только циферблат/виджет.
- Может ли alarm запускать `app-service/index.js` без предварительного ручного старта фонового процесса пользователем.
- Может ли виджет сам перерисоваться после фонового обновления файла, если его JS runtime заморожен.
- Поможет ли отдельная кнопка в приложении часов `Start background service`, как в старых версиях/паттернах Zepp OS.
