# Взаимодействие приложений WatchDrip2 (Android) и WatchDrip2_Zepp (Zepp OS)

На основе проанализированного исходного кода обоих проектов и предоставленного скриншота настроек, ниже подробно смоделирован рабочий процесс передачи данных об уровне глюкозы от сенсора до экрана часов Amazfit на базе Zepp OS.

Главная проблема, которую решает эта связка — **закрытость экосистемы Zepp OS**. Сторонние Android-приложения (такие как xDrip+) не могут напрямую общаться с часами Amazfit. Для этого требуется официальное приложение Zepp. Авторы WatchDrip обошли это ограничение с помощью локального веб-сервера.

## ⚙️ Роль настроек на скриншоте (Android)

*   **"Enable service" (Включено):** Запускает фоновую службу Android-приложения `watchdrip2`. Служба регистрирует `BroadcastReceiver` (`xDripReceiver.java`), который начинает перехватывать системные широковещательные сообщения от приложения xDrip+.
*   **"Enable web server" (Включено):** Это ключевая настройка для Zepp OS. Она запускает внутри Android-приложения миниатюрный локальный веб-сервер (используется библиотека `NanoHTTPD`). Сервер начинает слушать порт `29863` на локальном адресе телефона (`localhost`) и отдает актуальные данные по запросу на адрес `http://localhost:29863/info.json`.
*   **"Enable device" (Выключено):** Эта настройка отвечала бы за прямую прошивку бинарных циферблатов (патчинг) по Bluetooth для старых часов (Mi Band 4-6, Amazfit GTS/GTR 1-2). Для Zepp OS она **не нужна** и правильно, что выключена.

## 🔄 Пошаговый Workflow (Рабочий процесс)

### Шаг 1: Получение данных в Android (xDrip+ -> WatchDrip2)
1. **Сенсор/xDrip+:** Приложение xDrip+ получает новый замер сахара от сенсора (например, Dexcom или Libre).
2. **Трансляция (Broadcast):** xDrip+ отправляет системный интент в Android с данными о сахаре (значение, тренд, дельта).
3. **Перехват:** Фоновый сервис Android-приложения `watchdrip2` перехватывает этот интент.
4. **Обновление локального сервера:** `watchdrip2` парсит данные и обновляет свой внутренний кэш. Теперь локальный сервер `NanoHTTPD` готов отдавать свежий JSON по адресу `http://localhost:29863/info.json`.

### Шаг 2: Инициация запроса с часов (Zepp OS Watch)
5. **Кто запрашивает:** на часах ровно один владелец BLE-приёмника в каждый момент:
   * **Открыта страница приложения** (`page/index.js`) — она сама шлёт `CMD_GET_INFO` через свой `MessageBuilder` (через 3 с после открытия, затем раз в минуту, пока данные старше 60 с). Фоновый сервис в это время приостановлен Zepp OS.
   * **Страница закрыта** — continuous App Service (`app-service/index.js`) шлёт запрос по `Time.onPerMinute` (раз в минуту при активном экране, ~раз в 6 мин в глубоком сне) и по событию `force_fetch` (от карточки-виджета или `source=page_release` при закрытии страницы).
   * Будильники (`hmApp.alarmNew`, `@zos/alarm`) **не используются**.
6. **Отправка RPC:** `MessageBuilder.requestCb` по BLE; при `ready=false` сначала Shake. Подробности — `work_app.md` (Golden path v1.0.31).

### Шаг 3: Обработка запроса на телефоне (Side Service)
7. **Маршрутизация в Zepp:** Официальное приложение Zepp на телефоне получает этот BLE-запрос от часов.
8. **Side App (Скрипт-компаньон):** Zepp передает запрос невидимому фоновому скрипту `app-side/index.js` (который является частью приложения `watchdrip2_zepp` и устанавливается в приложение Zepp вместе с приложением для часов).
9. **Локальный Fetch:** Фоновый скрипт `app-side/index.js` выполняет стандартный HTTP-запрос `fetch("http://localhost:29863/info.json")`. 
10. **Связка с WatchDrip2:** Этот запрос обращается к **локальному веб-серверу**, который был запущен Android-приложением `watchdrip2` на Шаге 1!

### Шаг 4: Возврат данных и отрисовка
11. **Чтение JSON:** Сервер `NanoHTTPD` отвечает скрипту-компаньону, возвращая JSON строку с актуальными данными о глюкозе.
12. **Отправка на часы:** Скрипт-компаньон (`app-side/index.js`) запаковывает этот JSON обратно в RPC-ответ и отправляет его по Bluetooth на часы через приложение Zepp.
13. **Запись кэша:** получатель ответа пишет `info.json`: страница — сразу (ей можно писать при включённом экране); сервис — через `info.tmp.json` с проверкой размера (при включённом экране запись сервису запрещена ОС → данные ждут в памяти до следующего тика).
14. **Отрисовка:** страница, карточка-виджет и циферблат (appId 1121231) только читают `info.json` и обновляют UI (значение, цвет по порогам, стрелка тренда, дельта, «N мин назад»).

## 💡 Резюме
Android-приложение `watchdrip2` выступает в роли **локального API-сервера** на телефоне. А Zepp OS приложение `watchdrip2_zepp` выступает в роли **веб-клиента**, который опрашивает этот сервер через скрипт-прокладку в приложении Zepp. Это невероятно изящный хак, который позволяет передавать медицинские данные в закрытую экосистему смарт-часов вообще без использования интернета и облачных сервисов.
