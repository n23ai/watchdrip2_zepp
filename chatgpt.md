На скриншоте отображаются:

- `master` — локальная ветка на вашем компьютере.
- `origin/master` — локальная ссылка на ветку `master` на GitHub.
- `origin` — имя удалённого репозитория, обычно GitHub.

Это не две независимые версии проекта. `origin/master` — запомненное Git-состояние удалённой ветки после последнего `fetch/pull`.

В вашем репозитории сейчас:

```text
master        ahead 3
origin/master
```

То есть локальная `master` содержит 3 коммита, которых пока нет на GitHub:

```text
07d4747 add_app-side(config and log)
48c67c7 add_buttom and fix widget
d1cd734 рабочая версия 10 тиков
```

Также сейчас активна ветка:

```text
codex
```

Она совпадает с `origin/codex`.

Простая аналогия:

- `master` — ваша локальная рабочая папка.
- `origin/master` — копия состояния проекта на GitHub.
- `git push` отправляет ваши коммиты на GitHub.
- `git pull` получает изменения с GitHub.
- `git fetch` только обновляет информацию о GitHub, не меняя файлы.

Для новичка безопасное правило: работайте в ветке `codex`, сохраняйте изменения коммитами и отправляйте их в `origin/codex`. В `master` пока ничего не переключайте и не сливайте без необходимости.

- это исправляет конкретную гонку: страница открылась за несколько секунд до `Time.onPerMinute()`;

- не создаётся дополнительный постоянный таймер;
- не затрагиваются BLE, RPC и App Service.

`+10 с, +25 с, +45 с, +65 с`

- `Time.onPerMinute()` действительно является штатным способом continuous-сервиса: [framework.md:157](~/Documents/dev/zepp/specification/guides/framework.md:157).
- В App Service запрещены обычные таймеры вроде `setTimeout`: [framework.md:183](~/Documents/dev/zepp/specification/guides/framework.md:183).

По bridge уже наблюдалось: процесс оставался `Running`, но его `latestUsedTime` переставал обновляться. Значит, наличие процесса не доказывает, что тики продолжаются.

Правильный фикс:

1. App Service при каждом `TICK` записывает маленький служебный файл, например `bg-health.json`:

```json
{
  "version": 1,
  "runId": 12345,
  "tick": 17,
  "stage": "TICK",
  "tickAt": 1783981000000,
  "lastSaveAt": 1783980940000,
  "errorCode": ""
}
```

Без сахара, URL и ответа сервера.

2. При успешном запросе обновляется `stage: SAVE_OK`. При ошибке — `stage: HTTP_ERROR`, но `tickAt` остаётся свежим. Поэтому ошибка сервера не будет ошибочно восприниматься как смерть сервиса.

3. При открытии страницы контроллер проверяет одновременно:

```text
сервис отсутствует                  → start
сервис есть + tick младше 3 минут   → ничего не делать
сервис есть + tick старше 3 минут   → stop → дождаться исчезновения → start
```

4. `stop → poll → start` должен выполняться последовательно, с блокировкой операции и максимум одной повторной попыткой.

5. После `start` проверять отдельно:

```text
START_RET = 0
START_CB = success
сервис снова присутствует в списке
```

Появление первого `TICK` проверяется уже как отдельное доказательство живого сервиса, а не как часть мгновенного `start`-контроля.

6. Внутри App Service оставить `Time.onPerMinute()`. Встроенный watchdog может сбросить зависший BLE-запрос на следующем тике, но не сможет восстановить сервис, если сами тики перестали приходить. Поэтому восстановление выполняется при следующем открытии приложения.

`app-service/heartbeat.js` сейчас не помогает: он существует, но не зарегистрирован в `app.json` и не запускается.

Технически второй App Service добавить можно: спецификация разрешает несколько записей в `app.json`, но точное максимальное число не указано. При превышении системного лимита `start()` возвращает ошибку `7` — `number of services has reached the system limit`. Для continuous-сервиса система гарантирует только один экземпляр конкретного сервиса. ([framework.md:217](~/Documents/dev/zepp/specification/guides/framework.md:217))

Но предложенный watchdog не будет надёжным фиксированием.

`@zos/alarm` действительно может запускать App Service раз в минуту. ([other-apis.md:316](~/Documents/dev/zepp/specification/reference/device-app-api/other-apis.md:316)) Однако single-execution App Service ограничен 600 мс. За это время он может прочитать `bg-health.json`, но не может гарантированно выполнить:

```text
stop()
→ дождаться асинхронного complete_func
→ дождаться исчезновения из списка
→ start()
→ дождаться complete_func
```

`stop()` и `start()` асинхронные, поэтому их callback может прийти уже после завершения watchdog-процесса. ([app-service.md:65](~/Documents/dev/zepp/specification/reference/device-app-api/app-service.md:65), [app-service.md:128](~/Documents/dev/zepp/specification/reference/device-app-api/app-service.md:128))

Кроме того, watchdog может одновременно пересечься с минутным тиком основного сервиса и сам вызвать ту же гонку `stop/start`, из-за которой сервис уже ломался.

Теоретически можно разделить восстановление на два запуска:

1. Первый alarm-запуск обнаруживает старый тик и вызывает `stop`.
2. Следующий alarm-запуск проверяет исчезновение процесса и вызывает `start`.

Но это будет зависеть от точности alarm, состояния системы и возможности `@zos/app-service` управлять другим сервисом из single-execution. Спецификация гарантирует управление continuous-сервисом из Device App, а не работу такого watchdog-супервизора.

Правильнее оставить один continuous App Service:

- он пишет `bg-health.json` на каждом `TICK`;
- страница при открытии проверяет возраст последнего тика;
- если тик старше 3 минут — выполняет полноценный последовательный `stop → poll → start`;
- если тик свежий, сервис не трогается;
- ошибка HTTP не вызывает перезапуск, потому что тик при этом остаётся живым.

Итог: второй alarm-процесс можно сделать как экспериментальную диагностику, но рассчитывать на него как на надёжный автоматический watchdog в Zepp OS 3.0 нельзя. Надёжное восстановление через `stop/start` должно выполняться основным приложением, где нет лимита 600 мс.

### Рекомендуемая архитектура

Оставляем текущий continuous App Service:

```text
App Service
  → получает сахар раз в минуту
  → записывает info.json

watch-widget
  → читает info.json
  → показывает сахар, возраст и stale
```

Сам `watch-widget` не должен делать BLE, RPC или сетевые запросы. Тогда при взгляде на часы отображается последний успешно полученный сахар, например:

```text

```

Если сервис остановился, компонент покажет старое значение и возраст, например `18 min`, а также перечёркивание. Сам он сервис перезапускать не сможет.

### Важный нюанс

Отдельный пакет с `appType: "watchface"` не сможет просто прочитать наш `info.json`: у каждого Mini Program собственный изолированный каталог `/data`. [File System](https://docs.zepp.com/docs/guides/framework/device/fs/)

`watch-widget`, встроенный именно в наше приложение, вероятно, будет иметь доступ к его же данным, но это нужно подтвердить на реальных часах. Документация описывает саму регистрацию компонента, но почти не раскрывает его lifecycle.
